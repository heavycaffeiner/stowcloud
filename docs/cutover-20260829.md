# Handoff: engine rebuild, 2026-08-29

For the next agent picking up `refactor/core`. This is state and evidence, not
a plan. Where it makes a claim it names how the claim was checked, because
several claims in this rebuild turned out to be wrong, including one made
during the session that produced this document, and the ones that survived
were the measured ones.

## The rule that governs everything here

From `docs/refactor/README.md`: `go/internal/` is a **behavioural
specification only**. Nothing is copied into `go/engine/`, and that includes
comments. `scripts/verify.sh` runs `tools/freshscan`, which diffs the two
trees' comment lines and fails the build on a match. It caught one line in this
session's work. Do not try to satisfy it by paraphrasing a line you are
reading; read the code, decide what is actually true of the new code, and write
that.

### `admin.index.build`

`engine/lifecycle/open.go:278` builds the search service with no index:

```go
e.Search = svc.New(svc.Options{Clock: clk, CPUs: runtime.NumCPU()})
```

`Service.SetIndex(*index.NameIndex)` exists and is called from nothing outside
tests. `Build` checks `s.index()` first and returns `ErrNoIndex`. The
construction is a real decision, not a line: the index has to live somewhere on
disk, survive a restart, and be found again at boot. `index.WriteBase` and
`index.OpenBase` are the two ends of that.

The estimate route is bound and is the useful half already. It needs only
`search.ScanCorpus` and `search.EstimateNameIndex`, both free functions, so it
binds without any index existing. That is the ordinary sequence anyway: an
operator sizes the index before deciding to spend a full traversal on it.

### `admin.smb.apply`, and a hole behind the routes that are already bound

`publish.Publish` takes a `Deps` whose `Accounts` interface is two methods:

```go
PublishPasswdEntries(ctx context.Context, path string, gid uint32) error
PublishPassdb(ctx context.Context) error
```

`auth.Service` has the second and not the first. `smb.PasswdEntries(users
[]User, gid uint32)` renders the bytes, so the missing piece is the function
that reads the account list, maps each row id through `auth.SMBBaseUid`, and
writes the result.

**The more serious gap is not the route.** `lifecycle.Open` passes no
`RenderPassdb` and no `PassdbPath` to `auth.New`. Read `auth.Config`: a nil
renderer means every credential change stops at the database. The comment in
`smbcred.go` says what that costs:

> Deleting a row closes the protocol in the database and nowhere else: the
> daemon authenticates against the last file that was published, so a
> revocation stopping at the database leaves the sidecar serving the revoked
> credential.

So in a deployment with a sidecar, the three SMB routes bound this session
would write the database and leave the daemon serving the old password. **The
routes are bound; the publication path behind them is not wired.** I did not
fix it because the engine has no sidecar to publish to yet, and a renderer
writing to a path nobody reads would be theatre. Do not mistake the green tests
for a working revocation. Wire this together with `admin.smb.apply`, not after.

### `preview`: "blocked on `cmd/stowcloud`"

**False, and the route is now bound.** The entry said the engine had the worker
package while only the shipped command could host it, and that the shipped
command still runs the old tree, so thumbnails had to wait for the cutover.

What is actually in the tree: `engine/service/preview/worker/jailedworker` is
its own `main` package that calls `worker.Run(jail.Preferred)`. It builds
standalone, in about a quarter of a second, and it is the real decoder rather
than a test double. `preview.PoolOptions.Exe` names the binary the pool execs.
The default is this process plus a `preview-worker` argument, which is what
ties the two halves to one command, but it is a default and not a requirement.

So the route needed a handler and a construction, both of which are now in
`engine/lifecycle/thumbnail.go`, plus one field: `Options.PreviewWorker`. That
field exists because the engine is not yet the shipped command. A test binary
answers no `preview-worker` subcommand, so without it the first thumbnail
fails at exec with nothing pointing at why.

The conclusion I had drawn was that a subcommand of the host binary can only
be run by the host binary. That is true of the subcommand and false of the
decoder, which also ships as a command of its own. Nothing in the todo was
checked against the directory listing.

## What the thumbnail route does

The permission is the file's own, `Read|Download`: a thumbnail derives from
the bytes, so serving one to an account that cannot open the file hands over a
downscaled copy of it. Addressed by path like every other read, because a file
id is allocated lazily and a plain listing carries none.

Served from this origin rather than the content origin, unlike the file bytes.
What travels is a PNG this process wrote from pixels the jailed decoder
produced: none of the caller's bytes and none of their metadata reach the
response, so there is nothing left for a browser to be tricked by.

Driven against a running server with the real decoder, and every response
decoded by Pillow rather than counted:

```
small    PNG (256, 192)   tl=(240,30,30)  br=(20,20,20)
medium   PNG (512, 384)   tl=(240,30,30)  br=(20,20,20)
large    PNG (640, 480)   tl=(240,30,30)  br=(20,20,20)
```

The source was 640x480 with `(240,30,30)` in the top-left quadrant and
`(20,20,20)` elsewhere. The colours survive at the right corners, so the image
is neither rotated nor mirrored nor another file. The three sizes are distinct
and aspect-correct. A second fetch of the same URL returned bytes identical to
the first, which is the cache answering.

Refusals: a text file 501, an undefined size 422, a traversal 404, an absent
file 404, no credential 401. `Content-Length` matches the delivered body,
`Cache-Control` is `private, max-age=86400, immutable`.

**One finding recorded and not fixed.** An undecodable file answers 501 "not
supported by this build", which describes the build rather than the file. The
status is defensible; the message is not. It comes from the classifier, which
maps `preview.ErrUnsupported` to the `NotImplemented` class and then uses that
class's generic message, dropping the sentinel's own `preview.unsupported`
key. That is true of the whole preview family rather than of this route, so it
is a question for `apierr` and is noted in the handler.

## The defect found this session, and where the same shape lives

`smb.totp_policy` was read out of the settings document into
`Values.SMBTOTPPolicy` and then dropped. Nothing called `SetSMBTOTPPolicy`
outside tests. An operator who set the blocking policy kept running under the
permissive default: every account enrolled in a second factor held the protocol
access the operator had just revoked, and the settings screen showed the
revocation as applied. Fixed in `engine/lifecycle/settings.go`, applied after
`Auth` is built and before anything serves.

This is the second instance of one shape. `d2e677a` fixed the first: host
lists, proxy ranges and rate limits were all loaded and never assigned, so a
configured deployment ran as though nothing had been configured. **Assume there
are more.**

`tools/settingscheck` does not catch this class and is not meant to. Read its
header: it compares the client's request field names against key literals in
the loader, which catches a field the screen writes and no loader reads. This
defect was one step further down, a value the loader read correctly and no
consumer applied. Nothing currently checks that edge. If you want the class
closed rather than patched twice more, that is the tool to write.

The parse takes the blocking policy for an unrecognised name. Guessing
permissively would hand protocol access to exactly the accounts an operator
with an unusual value may have been trying to shut out.

## A claim I made and then disproved

While writing this document I noticed `engine/lifecycle/search.go` hand-rolled
its own SSE writer instead of using `handler.SSEFrame`, which carries an
explicit line-break check. I wrote that up as an injection hole: a file name
containing a newline splitting a frame so a client receives an event the server
never sent.

**It was not one.** The mutation that should have proved it survived, so I
checked directly: `json.Marshal` escapes `\n` inside a string, and the raw
bytes never contain a line break. The original writer was correct. The two
encoders produced identical output.

The change is still in the tree, because one encoder is better than two, and so
is the test, because it pins the outcome rather than either mechanism. Both
comments now say what was measured instead of what I assumed. The test does
discriminate: a writer that interpolates the name into the frame without
escaping splits the stream and the test catches it.

Recording this because the same reflex, seeing a shared helper unused and
concluding the duplicate must be missing its guard, will look just as
convincing next time.

## What the tests are worth

Twelve mutations against the SMB and index work, all caught: removing either
`reconfirm`, the admin check on the estimate, each of the four state projection
fields, the `revertible` flag, the weak-password floor, dropping the formula,
and both policy branches.

Nine more against the thumbnail route. Six caught: the three sizes collapsing
to one, an undefined size accepted, the content type misdeclared, the chain's
`nosniff` removed, the cache directive turned public, and the cache header
dropped entirely. Three absorbed, all three diagnosed:

- **Weakening the permission to `Read` alone changed no answer**, because
  `preview.Service.Get` requires `Read|Download` and refuses first. The same
  redundancy `filesRead` already carries, and recorded the same way.
- **Removing the credential check changed no answer**, because the route is
  declared `AccessAnyCredential` and the middleware refuses before the handler
  runs.
- **Removing the handler's `nosniff` changed no answer**, because the chain
  sets it on every response. That one was not redundancy worth keeping: the
  line was deleted, and the test now asserts on the delivered header, which a
  mutation of the chain does catch.

Three survivors from the earlier work, also diagnosed rather than left
standing.

- **`revertible` as a constant `true` passed.** Every account in the test was
  revertible, so the constant matched. An opted-out account separates them and
  that case is now in the file.
- **Misspelling `"block"` still passes, and always will.** The name then falls
  to the default, which also blocks. A genuinely equivalent mutant. Recorded in
  the doc comment on `smbTOTPPolicyOf`; what the tests pin instead is the
  permissive branch, the one whose loss would be a security change.
- **Removing the SSE line-break check passed**, which is what disproved the
  claim above.

That is the pattern to copy. Diagnose why a mutant survived, and when the
answer is that it is equivalent or that the premise was wrong, write the
finding into the code beside the thing it describes. A surviving mutant with no
explanation recorded is indistinguishable from a test that does not work.

**Two harness traps already paid for.** Do not repeat them.

1. Counting `--- FAIL` lines scores a panic as absorbed, because a panicking
   test never prints that line. Trust the exit code.
2. A mutation that did not apply, or did not compile, must be reported as such
   and never scored. This session's script prints `NOT-APPLIED` and
   `NO-COMPILE` and refuses to substitute unless the pattern matches exactly
   once. Two mutations hit those states here, and one of them, a type assertion
   against `map[string]any` when the value is a `SearchHitView` struct, would
   have read as an absorbed result and been wrong.

## What was driven against a running server

`cmd/stowcloud` still imports `internal/`, so the engine cannot be booted by
the shipped command. `go/tools/enginedrive` exists for this: it calls
`lifecycle.Open`, seeds an admin and an ordinary account, mounts, and prints
the base URL and an app password. Reopening the same directory exercises a
restart rather than a fresh boot.

Two things about driving it by hand, both of which cost me time:

- The login body field is `login`, not `username`.
- The CSRF header is `Sc-Csrf`. Sending `X-CSRF-Token` gets a 403 that looks
  like a permission failure.

This session's routes, live:

```
set without current            401
set with a wrong current       401
set a five-character password  422
set correctly                  200
opt out                        200, enabled:false alongside opt_out:true
clear after opting out         200, revertible:false
no CSRF header                 403
no session                     401
estimate as administrator      200
estimate as an ordinary user   403
```

The estimate reported 4 files and 26 name bytes. The corpus on disk has exactly
4 files, and `find -printf '%f' | wc -c` gives exactly 26. The formula claims
14 distinct trigrams and the four names contain exactly 14. That is the point
of the route returning its derivation: the arithmetic can be checked against
the disk instead of believed.

Earlier sessions' evidence is in `docs/refactor/cutover.md` under "What has
been verified about the engine so far" and is not repeated here.

## The three things blocking a cutover

Unchanged from `cutover.md`, which has the measured line counts.

1. **Six routes**, above.
2. **dav and compat have their vocabulary and none of their handlers.**
   `engine/http/dav` is 1,759 lines of If-header grammar, XML scanning,
   PROPFIND and PROPPATCH parsing, multistatus writing, href encoding and the
   method-to-permission table. There is no handler for a single method. The old
   tree's equivalent is roughly 2,000 lines beside its parsing. `compat` is the
   same shape at 1,178 against 4,356. An earlier version of the document called
   this "a mount" and was wrong.
3. **The public link surface is absent entirely.** Five routes under
   `/s/{token}`: landing, password gate, download, zip, drop upload. The engine
   binds link creation, listing, update and deletion, so links can be minted
   and never opened. The old tree serves 101 routes against the engine's
   87-entry table and this is most of the difference.

Deleting `internal/` today removes WebDAV, the vendor compatibility layer and
every public link from a running deployment.

## Suggested order

1. **Wire `RenderPassdb` and `PassdbPath`, then bind `admin.smb.apply`.** The
   unwired publication path is a live correctness hole behind routes that
   already answer 200, which makes it worse than an unbound route.
2. **Bind `system.setup.get` and `system.setup.post`.** The gate is built and
   tested; the handler is about 250 lines in the tree it replaces. This is the
   best-understood of the remaining five.
3. **Port the events hub** (~300 lines) and wire a watcher into
   `lifecycle.Open`.
4. **Construct the name index and bind `admin.index.build`.**
5. **dav, then compat.** Size it before starting.
6. **The public link surface.**

Rewiring `cmd/stowcloud` and deleting `internal/` is an afternoon after those.

One thing to do at the cutover rather than before it: `Options.PreviewWorker`
exists because this tree is not the shipped command. Once `cmd/stowcloud`
hosts the engine, the pool's default finds the `preview-worker` subcommand in
the same binary and the field can go. Leaving it would be a second way to
name a decoder, and the reason for the first would be gone.
