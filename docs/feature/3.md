# Phase 3: Database-only configuration, sc.toml removed

## Goal

Remove the config file entirely. The database is the single source of every
setting; the admin UI (and phase 6's emergency UI) is the only editor. Legacy
`sc.toml` deployments are not migrated: an existing install reconfigures
through the first-run flow.

## Status

Done. `runtimecfg.Values` carries the full surface with `check.go` holding the
rules both the save and the boot read; `server.FromValues` replaces
`server.Load`; `serve` boots from `--data-dir` alone; migrations 10 (one kind
of share) and 11 (`config_secret`) landed; the check endpoint and the dry-run
button are gone; the toml files, the loader and the BurntSushi dependency are
deleted.

Four things the implementation settled that the plan below did not:

- **`stowcloud settings get|set`.** With no file there was no way back into a
  deployment whose stored bind address stops it answering, and the emergency
  interface needs a socket too. One command writes a section against a data
  directory nothing is serving. It is the only editor outside the web UI.
- **An empty app-host list admits every host.** That is the first boot: no
  name has been chosen, so there is nothing to check against, and refusing
  every host leaves a server nobody can reach to name it. Setup writes the
  list and the guard is the origin check it always was from then on. Found by
  booting an empty data directory: it started and answered every request with
  "misdirected request".
- **The SMB grants are conditional on SMB being on.** The jail granted
  `/config/smb` unconditionally, and a grant names a path that has to exist,
  so a first boot with no sidecar refused to start over a directory nothing
  was going to use. Same find, same run.
- **A certificate that does not name the app host is regenerated.** The pair
  is minted before anyone has said what the deployment is called, so it
  covers localhost only. Keeping it would tell every browser reaching the
  deployment by name that the certificate is for something else, forever.

## Current state

`server.Load` parses `sc.toml` into `server.Config`; `runtimecfg` layers DB
overrides on top of it ("the file is the floor"). The serve path, `setup`,
`healthcheck`, `gc`, `smb-sync` and the sandbox spec all take the file path as
an argument. This phase deletes the floor.

## Design

### Bootstrap values

A process needs a handful of values before it can open the database. These
stop being configuration and become process arguments with fixed defaults:

- `--data-dir` (default `/var/lib/stowcloud`): where the store lives.
  Everything else is read from the store found there.
- That is the whole list. Listen address, hosts, proxies, shares, SMB,
  hardening: all live in the database.

The healthcheck cannot read the database: it runs as a second process while
serve holds the store. Serve writes a small probe snapshot (listen port, app
host) into the data dir on every start and settings change, and healthcheck
reads that instead of a config file. It already reads the TLS material from
the same directory, so this adds one file to an existing pattern.

### First boot

A data dir with no settings document is a first boot. The server starts with
built-in defaults: bind `0.0.0.0:8443` on all interfaces, no app-host
restriction until setup completes (the setup gate is the only thing served),
no shares. Phase 5 builds the full first-run UX on top of this; this phase
only guarantees the server starts and serves the setup gate from an empty
data dir.

### Settings schema

`runtimecfg.Values` grows to cover everything `server.Config` held: listen
address, app hosts, trusted proxies, rate limits, hardening policy, DB guard,
SMB (render config, config dir, agent socket, service GID), OIDC, and shares.
The store keeps the existing one-document-per-section shape. Validation moves
with the values: what `server.Validate` refused at parse time, the settings
save now refuses at save time with a named finding, and the boot-time read
clamps or drops with a logged line, never refuses to start.

Two consequences of losing the file:

- `runtimecfg`'s base-over-override layering ("the config file is the
  floor") collapses: the compiled-in defaults become the floor and the
  stored document is the only override. `Holder.Base()` and the seeding path
  simplify accordingly.
- The config-share versus admin-share split disappears. Every share is a
  database share; `ConfigDefined`, `configShareNames` and the screen's
  hidden-delete behavior for config shares go away, and the fixed-ID
  registration loop in `serve.go` folds into `ReloadPersistedShares`.

The OIDC client secret moves into the store encrypted under the master key,
through the same `secret` machinery the SMB credentials already use; it is
never stored plaintext in the settings document.

### Save-time dry run, no button

Every settings save runs the probes (`settings_check.go`) first and refuses
on any blocking finding. The separate check endpoint and the UI's dry-run
button are removed: save is the dry run plus the write. The probe code is
kept; only its second entry point goes.

### What gets deleted

- `server.Load`, the `raw` struct, the BurntSushi/toml dependency.
- The config-path argument from every subcommand; `setup` and `healthcheck`
  take `--data-dir`.
- `deploy/sc.toml.example`, `deploy/sc.quickstart.toml`, testbed toml files;
  compose files drop the config mount.
- The sandbox spec's config-file grant.
- The two share kinds: `ConfiguredShare`, the identity and trash override
  tables, `ConfigShares`/`config_defined` and the screen's badge and hidden
  delete.

### Sandbox interaction

The jail spec is built from settings that now come from the DB, which is read
after the store opens but before the sandbox is applied. Share grants for
admin-created shares already work this way; config shares join them. A share
added at runtime still requires the soft restart phase 4 provides for the
jail to grant it, same as today.

## Work items

1. Extend `runtimecfg.Values` and the store schema to the full config
   surface; move `server.Validate` rules into save-time checks and boot-time
   clamps.
2. Rework `serve` to boot from `--data-dir` alone: open store, read settings,
   build config, apply sandbox, serve. Empty store serves the setup gate on
   all interfaces.
3. Convert the other subcommands: `setup` and `healthcheck` take
   `--data-dir` (`masterkey rotate` already does; `gc` and `smb-sync` are
   unimplemented stubs and only their usage text changes).
4. Delete the toml path: loader, dependency, example files, compose mounts,
   docs references.
5. Remove the check endpoint and fold probes into save; keep probe code.
6. Update tests that construct configs from toml fixtures to construct
   `Values` directly.

## Acceptance criteria

- `stowcloud serve --data-dir /tmp/x` on an empty dir starts and serves the
  setup gate over TLS on 0.0.0.0:8443.
- No file named `sc.toml` is read, shipped, or mentioned anywhere in the
  repository outside historical docs.
- Every setting that `sc.toml` could express is settable from the admin API,
  is validated on save, and survives a restart.
- A stored setting that fails boot-time validation is clamped or dropped with
  a log line; the server still starts.

## Depends on

Nothing, but phases 4 through 7 all build on it.
