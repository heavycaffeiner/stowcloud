# Phase 5: First-boot flow

## Goal

A fresh install is reachable from the local network immediately, walks the
operator through one token-gated setup form, and lands on a working home
screen even when nothing has been configured beyond the required fields.

## Status

Done. The pre-setup opening is bounded by `smb.IsPrivate` in
`go/internal/httpapi/mw/hostguard.go`; the form's four sections are handled by
`SetupComplete` in `go/internal/httpapi/handler/setup.go` (network probe,
account, first share, listener swap) and drawn in `web/src/routes/setup`; the
empty home is in `web/src/routes/(app)/b/[...path]/+page.svelte`. Tests:
`go/internal/httpapi/mw/firstboot_test.go`.

Two things the implementation settled:

- **The lockout finding is a warning here and a block on the settings
  screen.** An operator browsing by address while naming the DNS name the
  deployment will actually be reached under is doing the right thing, and no
  rule can tell that apart from the mistake. Blocking it would make the form
  impossible to complete for that deployment. The page stays put and shows
  the warning rather than navigating away, because a warning nobody read is
  the same as no warning.
- **The first boot is admitted from private addresses only.** Phase 3 left an
  empty host list admitting everything, which is what made an unconfigured
  deployment reachable at all. That is too wide: a box published before
  anybody configured it would be offering the account-creation form to the
  internet. The peer address bounds it.

## Current state

Phase 3 already makes an empty data dir boot and serve the setup gate on
0.0.0.0:8443. The existing setup flow issues a one-time token and creates the
first administrator. What is missing is the full first-run form, the NIC-wide
reachability guarantee, and the empty-home experience.

## Design

### Reachability before setup

On first boot the server binds 0.0.0.0, which covers every NIC. The app-host
guard is the risk: it must not lock out a LAN operator before setup. Until
setup completes, the guard admits any request whose peer address
`smb.IsPrivate` accepts (RFC 1918, loopback, link-local, unique-local, and
the carrier-NAT block, so a tailnet works too; the classification the SMB
side already uses, reused rather than redefined), and serves only the setup
gate. After setup, the configured app-host list takes over in full.

### The setup form

Reached with the one-time token (printed at first start and by `stowcloud
setup`). One form, in order:

- **App hosts** (required): the names the server will answer for. Prefilled
  with the host the operator is currently browsing from.
- **Trusted proxies** (optional, may stay empty).
- **Bind address** (optional; empty means `0.0.0.0:8443`).
- **First share** (optional): name and host path. Skippable.
- **Administrator account**: the existing credential creation, unchanged.

Every field is validated with the same save-time probes as the settings
screens, so the form cannot store a value the settings screen would refuse.
Submitting writes the settings document, creates the administrator, spends
the token, and soft-restarts the serve layer (phase 4) so the bind address
and host guard apply immediately.

### Empty home

A deployment with no shares shows "Nothing Here!" with a new-share button and
one line of guidance ("Press this button to set up your first shared
folder"). The button opens the existing admin share-creation flow for
administrators; a non-admin sees the message without the button.

### Prefilled hosts and lockout safety

If the app-host list the operator submits does not include the host they are
currently connected through, the probe warns (not blocks): they may genuinely
be setting up for a different name behind a proxy. The warning names the
current host so the mistake is visible before it locks them out.

The same finding blocks on the settings screen, where the guard is already
live and the next request would be refused. `setupFindings` is the one place
that downgrades it, so the difference is deliberate and visible rather than
two copies of the rule drifting apart.

## Work items

1. Pre-setup host-guard mode: private/link-local admission, setup-gate-only
   routing.
2. Extend the setup form (web/src/routes/setup) with the four sections and
   probe-backed validation.
3. Setup submission path: settings write, admin creation, token spend, serve
   layer soft restart, redirect to home.
4. Empty-home screen with the new-share call to action.
5. Tests: fresh boot reachable from a non-loopback address, setup with only
   required fields lands on the empty home, host-list warning fires when the
   current host is missing.

## Acceptance criteria

- `docker compose up` on a clean volume, then browsing to `https://<lan
  ip>:8443` from another machine on the LAN, reaches the setup gate with no
  file edited.
- Completing setup with every optional field empty lands on the "Nothing
  Here!" home with a working new-share button.
- The setup form refuses the same values the settings screens refuse, with
  the same messages.
