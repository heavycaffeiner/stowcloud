# Phase 6: Emergency mode

## Goal

A safe-mode editor for the settings database that answers even when the
normal server cannot: reachable at `ip:port/emergency` from the local network
at all times, admin credentials required, and automatically fronted when the
core engine has crashed. This replaces what editing `sc.toml` used to fix.

## Status

Done. The mux is `go/internal/emergency/emergency.go`, mounted under the
normal server by `go/internal/server/wire.go` and served standalone by
`go/internal/server/emergency.go` and `go/cmd/stowcloud/emergency.go`. The
screen is `web/src/routes/emergency/+page.svelte` over
`web/src/lib/api/emergency.ts`. Tests: `go/internal/emergency/emergency_test.go`.

Four things the implementation settled beyond the plan:

- **The probes moved to their own package**, `go/internal/settingscheck`.
  They used to live beside the handlers and reach into the engine's Deps,
  which the emergency process does not have. Three surfaces now run the one
  copy: the settings screen, the first-run form, and this door.
- **The lockout finding is a parameter, not a rule.** `settingscheck.Lockout`
  is `LockoutBlocks` on the settings screen, where the guard is live and the
  undo request would be the one refused, and `LockoutWarns` on the two
  screens the guard does not gate. Encoding it once is what stops the three
  copies drifting.
- **The degraded process stays up rather than exiting.** Everything after the
  store and the auth service open falls into `degrade`, which brings up the
  emergency listener with the failure in the banner. The one exception is the
  sandbox: it is applied before anything is opened, and opening the store
  after refusing to confine the process is exactly what the refusal said not
  to do, so that path prints the `--emergency` command instead.
- **`serve` now takes the instance lock.** Nothing did, so `--emergency`
  cheerfully started beside a running server and both wrote the same
  databases. A repair applied to a document the running server then
  overwrites is worse than a refusal.

One real bug found on the way, unrelated to the door but caught by its
end-to-end run: `MergeSettings` replaced a section wholesale, so a save that
named one field erased every field beside it. The first-run form saving an
app-host list dropped the bind address an operator had seeded, and the server
came back on a port nobody asked for with nothing in the log. The merge now
reaches inside the section; clearing a field is explicit.

## Threat model first

This page edits every setting including the host guard and the share list, so
it is the most valuable target in the product. Constraints that hold in every
mode:

- **Network scope.** Requests are admitted only when the peer address (after
  trusted-proxy resolution, and refusing any forwarded header when the peer
  is not a trusted proxy) is one `smb.IsPrivate` accepts: RFC 1918,
  loopback, link-local, unique-local, and the carrier-NAT block, the same
  classification the SMB side uses. Everything else gets 404, not 403: the
  page does not confirm its existence to the outside.
- **Authentication.** The registered administrator's credentials, checked
  against the same auth store and rate limiter as the normal login, plus the
  admin's TOTP when one is enrolled. No token shortcut, no recovery bypass.
- **Surface.** The emergency mux serves exactly: the login, the settings
  read/write API (same validation as the normal path), and a restart action.
  No file browsing, no share content, no user management.
- **Audit.** Every emergency-mode login and settings write is an audit
  event marked as emergency-mode.

## Design

### Two ways in

1. **Always-on route.** The normal serve layer mounts `/emergency` under the
   constraints above. It exists even when everything is healthy, because the
   moment it is needed is not the moment to be starting things.

   It is mounted outside the request chain, which is load-bearing: the
   chain's host guard is one of the things this door repairs, and a repair
   screen behind the guard it repairs is a screen nobody can reach. The peer
   address is what guards it instead, resolved from the same live trusted-proxy
   set the chain reads. What replaces the chain's CSRF step is the session
   cookie's `SameSite=Lax` plus an Origin-against-Host comparison; the
   comparison is against the request's own Host rather than the declared
   app-host list, because that list is exactly what may be wrong.
2. **Standalone flag.** `stowcloud serve --emergency` starts only the
   emergency layer: store, auth, settings, the emergency mux. It binds the
   stored listen address when the store yields one, else `0.0.0.0:8443`, so
   the address an operator already knows keeps answering. For the case where
   the full engine cannot come up at all (bad hardening policy, share root
   that panics the wiring). It uses none of the engine packages, so a bug
   there cannot take it down.

A data dir with no administrator yet has nothing emergency mode can
authenticate; both entrances answer with a pointer to the setup flow instead
of a login that cannot succeed.

### Crash fronting

The serve-layer supervisor (phase 4) watches the engine domain. When the
engine has crashed or failed to build, the serve layer stays up in degraded
mode: every non-emergency route answers with a redirect to `/emergency`, so
browsing to `https://ip:8443/` lands on the emergency login with a banner
naming what failed. When the process itself cannot stay up, the standalone
flag is the fallback, and the crash loop's log says so:
`run with --emergency to repair the configuration`.

### What it edits

The same settings document, through the same `runtimecfg` validation, with
one difference: the save-time probes that need the engine (share-path checks
against live roots) degrade to filesystem-level checks, and the response
marks which probes were skipped. A save from emergency mode takes effect on
the next normal start.

### TLS

The standalone mode reuses the data dir's existing certificate. A data dir
without one gets a fresh self-signed certificate, same as first boot.

## Work items

2. Mount under the normal serve layer; degraded-mode fronting on engine

3. `--emergency` standalone path in `serve.go`, engine-free.
4. Emergency-mode audit marking.
5. Web UI: minimal settings editor page (reuse the settings components where

6. Tests: external address gets 404, wrong credentials rate-limited, engine
   crash redirects `/` to `/emergency`, standalone mode boots with a corrupt
   hardening setting and can fix it.

## Acceptance criteria

- With a healthy server, `https://<lan ip>:8443/emergency` serves the login;
  the same URL from a non-private source address returns 404.
- With a settings value that makes the engine fail to build, the server comes
  up degraded and `/` redirects to `/emergency`; fixing the value there and
  restarting recovers the server.
- With a store the full server cannot even wire, `--emergency` boots, admits
  an admin, and can edit the offending value.
- Every emergency write appears in the audit log marked emergency-mode.
