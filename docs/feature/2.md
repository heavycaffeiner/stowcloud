# Phase 2: Chunk upload cache spool

## Goal

Let chunk uploads land on a fast cache volume (a separate directory, disk, or
tmpfs) instead of the destination directory, and merge into the destination
part file continuously so the cache never holds more than a bounded share of
its volume. Writing straight to the destination stays the default; the cache is
opt-in.

## Motivation

Two problems, one mechanism:

- **Throughput.** When the network is faster than the destination disk, chunks
  queue behind destination I/O. A cache on a faster volume (NVMe, tmpfs)
  absorbs the burst and the merge drains at disk speed.
- **Capacity mismatch.** The cache volume can be much smaller than the
  destination (128 GB root fs versus a 4 TB LVM volume). A 200 GB upload must
  work anyway, which means the cache is a window over the file, not a copy of
  it: chunks are merged out and deleted as the upload proceeds.

`go/internal/upload/cache_test.go`.

Three things the implementation settled that the plan below left open:

- **The mode is fixed at session creation**, recorded in `cache_dir`. A
  switch flipped mid-upload cannot move bytes that are already in one place
  or the other.
- **Name-ordered sessions never use the cache.** They already spool
  out-of-order chunks to files of their own and assemble by name; the cache
  would be a second staging layer under the first.
- **The merger never reads above the committed contiguous prefix.** A cache
  file exists before its range is recorded, because the range is recorded
  only after the checksum passes; merging early would put bytes the client
  is about to resend into the part file.

## Design

### Modes

- **Direct (default).** Exactly today's behavior: the part file and the spool
  directory live in the destination share, `PutChunk` pwrites into the part
  file. No new moving parts.
- **Cached.** Chunks are written to a cache spool first. A merger drains
  contiguous data into the destination part file and deletes drained chunk
  files. Enabled by an admin toggle; the spool location is fixed at
  `<data_dir>/spool`, not configurable. Fixed on purpose: the data dir is
  already inside the Landlock domain, so the toggle applies live with no
  engine restart, and there is no path setting to validate or get wrong. An
  operator who wants a faster or larger spool mounts a volume (tmpfs, NVMe)
  at that path; the engine only sees a directory.

### Cache budget

The cache may use at most 20% of its volume's free space, measured live
before each chunk is taken. When the spool is at its budget:

- If the merger has contiguous data to drain, the write waits for it, bounded
  by the request's context and by a ceiling on how long one chunk waits.
- If it has not, and this chunk is the one that would extend the contiguous
  region, it is taken: refusing it would refuse exactly the chunk that
  unblocks the merge.
- Otherwise the missing bytes are the ones the client has not sent, so the
  chunk is refused with a retryable 503 and a Retry-After and the client
  backs off instead of the server buffering unbounded holes.

The budget is checked before a chunk is written rather than during it, so the
spool can overshoot by one chunk per client in flight. Enforcing it mid-body
would mean tearing up a chunk that is already half written.

The budget is a live measurement, not a number captured at startup: another
program filling the cache volume shrinks the budget immediately.

### Merger

One goroutine per active cached session, owned by the engine:

- Tracks the contiguous frontier (the intervals bookkeeping in
  `go/internal/upload/intervals.go` already computes this).
- Appends contiguous cached data to the destination part file with
  `CopyRange`, fsyncs the part file, records the new frontier, then deletes
  the drained cache file. Order matters: data is durable in the destination
  and the frontier is recorded before the cache copy disappears, so a crash
  never loses received bytes. A crash mid-sequence re-merges the same range,
  which is idempotent.
- One step is bounded, so a chunk larger than the bound drains across several
  and the loop can see its cancellation in between. The cache file survives
  until its last byte is in the part file.
- A chunk is written under a staging name and renamed into place once it is
  whole and durable. The staging name does not parse as a chunk, so the
  merger cannot see a file that is still being written.
- On finalize, drains the tail, then hands over to the existing finalize path
  unchanged (verify, publish). Finalize does not know which mode fed the part
  file.

### Crash and restart

The recommended spool is a tmpfs and a reboot empties one, so a restart
cannot trust the recorded intervals: a session claiming bytes that are gone
would answer a resuming client with an offset whose data does not exist.
`RecoverCache` runs before the first request and cuts each cached session's
recorded set down to the intersection of what it claims and what is actually
there: everything below the merge frontier (in the part file) plus the cache
files still on disk. An upload resumes from less than it had rather than from
a lie.

The sweep gains a pass over the spool: a cache directory whose session row is
gone is debt no walk of the shares can find, because the spool is not a share
and the row is the only thing that names a directory in it.

### tmpfs note

A volume mounted at `<data_dir>/spool` works with no special casing: the
budget probe reads that volume's size like any other. The docs point at a
tmpfs mount there as the recommended setup for RAM-sized bursts; the engine
does not mount or manage one.

## Acceptance criteria

- Direct mode passes the existing upload test suite unchanged.
- A cached upload larger than the cache budget completes, and cache usage
  never exceeds 20% of the cache volume's free space during it.
- Killing the server mid-upload and restarting loses no acknowledged chunk.
- A read-only or uncreatable spool directory is refused when the toggle is
  saved, with a named finding, not discovered at upload time.
- Toggling the cache on and off requires no restart of any kind.
