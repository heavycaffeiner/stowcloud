# Phase 4: Isolated network layer and soft restart

## Goal

Settings that today say "restart required" instead take effect the moment they
are saved, by restarting only the layer they touch. The layers that cannot be
mutated live (listener bind address, TLS, share set under the sandbox, SMB
publication) are isolated so that restarting them does not kill the process or
drop unrelated work.

## Status

Done. `server.Serve` in `go/internal/server/supervisor.go` owns the listener
and swaps it; `server.New` returns one instead of an `*http.Server`;
`applySaved` in `go/internal/httpapi/handler/admin_settings.go` classifies
every save into `live | serve_restarted | engine_restart | reserved`;
`RequestRestart` and `ActiveWork` are wired in `serve.go`; the restart
endpoint, its button and its two dialogs are gone, and the busy refusal moved
onto the saves that now take the restart. Tests:
`go/internal/server/supervisor_test.go`, `go/cmd/stowcloud/jailpath_test.go`.

Three things found by running it rather than reading it:

- **CSRF froze the host list.** `mw.CSRF` took `hosts.App()` as a slice when
  the chain was built, so an app host saved afterwards reached the host guard
  and not the origin check: every state-changing request from the new name
  answered `csrf.origin_refused`. It takes the holder now. An empty list
  admits, matching the guard's own first-boot rule.
- **The dedicated network route dropped `bind`.** `PATCH .../network` had its
  own handler that decoded two fields, so the address in the same section was
  silently discarded while the response said success. That route is gone: the
  generic section handler owns the whole section and pushes the two live
  holders itself.
- **A new share only sometimes needs the restart.** `PathInJail` compares the
  path against the domain the sandbox was actually built from, so a folder
  beside an existing share is reachable at once and only a folder under a
  parent the domain never saw costs a restart.

## Current state

App hosts and trusted proxies are already live: holders read them per
request. The restart endpoint exists but is dead: `handler.Deps.RequestRestart`
is declared and called, yet nothing in `wire.go` or `serve.go` assigns it, so
the button answers 202 "restarting" and nothing happens. Fixing that wiring
is part of this phase, not a separate bug.

The jail grants each share's parent directory, so a share added beside an
existing one already works without any restart. What needs the engine
restart is a share under a parent the domain has never seen, plus the bind
address and TLS changes, which today need the (broken) process restart. SMB
config push to the sidecar via the control socket already applies without a
container restart.

## Design

### Two restart domains

- **Serve domain.** The listener, the TLS config, the HTTP mux and everything
  request-scoped. Restarting it means: build the new listener, swap it in,
  drain the old one with a deadline. In-process, no exec. This covers bind
  address and TLS changes.
- **Engine domain.** The sandboxed core: share roots, the jail. Landlock and
  seccomp cannot be widened in place, so a share under a new parent still
  needs a process restart; a share under an already-granted parent needs
  nothing, and the save says so instead of assuming the worst. The engine
  restart is the supervisor restart, actually wired this time: the exit is
  scheduled after the response is written, and phase 4 makes it automatic on
  a save that needs it (after the probes pass) instead of a separate button,
  with the in-flight-work refusal and force flag kept.

### The wiring change

`serve.go` splits its single construct-everything path into:

1. Build the engine (store, core, upload, watch, auth): once per process.
2. Build the serve layer (listener, mux, TLS) from a `Values` snapshot: cheap
   and repeatable.
3. A supervisor loop that rebuilds layer 2 when a saved change touches it.

A saved change is classified: live (applied via holders, nothing restarts),
serve-layer (listener swap), or engine-layer (process restart with the busy
check). The settings response tells the UI which happened, replacing the
`applied_live`/`restart_required` pair with a single
`applied: live | serve_restarted | engine_restart | reserved`. The fourth is
for a build with nothing wired to apply the change, which is honest rather
than a success that changed nothing.

### Listener swap

New listener binds first; failure to bind refuses the save with a named
finding and the old listener keeps serving, so a typo in the bind address
cannot take the server offline. Then the old listener stops accepting,
in-flight requests get the same 15 s drain deadline the shutdown path
already uses, and the old socket closes. Binding after the jail is applied
already works today (the listener binds after `applyJail` in `serve.go`), so
the sandbox does not constrain the swap.

### UI

The dry-run button is gone (phase 3). The restart button is gone: saving is
applying. The one remaining prompt is the engine-domain busy refusal, which
keeps its counts-and-force dialog and now hangs off the saves that take the
restart rather than off a button of its own. `force` rides in the section
body, so the retry is the same save with one field added.

   refused without force.

## Acceptance criteria

- Changing the bind address from the admin UI takes effect without the
  container restarting, and an in-flight download on the old listener
  completes.
- A bad bind address is refused at save; the server remains reachable.
- Adding a share beside an existing one applies with no restart at all;
  adding one under a new parent applies after an automatic engine restart,
  with the busy refusal when uploads are active.
- No settings screen shows a dry-run or restart button.
