# Phase 7: Failure visibility and SMB apply verification

## Goal

Problems the requirement says must never be silent: a share whose path has
disappeared, an engine crash, and an SMB change that did not actually reach
smbd. Each becomes something a user sees and an administrator can fix, not a
hidden entry or a quiet crash.

## Status

Done, except item 3 of the SMB section (see below).

A broken share is registered rather than dropped (`core.RegisterBroken`,
`shareEntry.brokenErr`), listed with its reason on the admin screen and in
every user's root list, and answered with `share.broken` / 503 naming the
folder rather than `fs.not_found`. `server.WatchShares` re-probes every root
every 30 seconds in both directions. Retry is `POST
/api/admin/shares/{id}/retry`. The crash-loop conclusion is
`cmd/stowcloud/failtrack.go`. The SMB republish outcome now rides on the
response of the write that triggered it. Tests:
`go/internal/core/brokenshare_linux_test.go`,
`go/cmd/stowcloud/failtrack_test.go`, and the new case in
`go/internal/server/smbsink_test.go`.

Four things the implementation settled beyond the plan:

- **The staleness probe asks about the path, not the descriptor.** The plan
  named an errno pattern on the root handle. There is none: holding the
  descriptor is what keeps the filesystem alive, so after an unmount the
  handle still stats and still reports the same device. `ShareRoot.Alive`
  resolves the configured path afresh and compares device and inode against
  what registration recorded. It is the one path resolution in `vfs` that does
  not go through the anchor, and it decides only whether to mark a share
  broken, never what a request may reach.
- **A broken share is not `ErrNotFound`.** Its own `core.ErrShareBroken` and
  its own wire code, because the path the caller named is perfectly good:
  telling somebody their folder does not exist when a drive did not come back
  sends them looking in the wrong place.
- **All three repairs clear the health degradation at the moment they run**,
  rather than at the next probe pass. Removing a broken share is the one that
  matters most: nothing re-probes a share that no longer exists, so a delete
  that did not clear it would leave the deployment degraded over it forever.
- **The crash-loop hold does not exit.** Three failures inside a minute is
  reported and put in the emergency banner, and the process stays up serving
  the repair door. Exiting would hand the spin back to the supervisor, which
  is the loop rather than the fix.

Two real bugs found on the way:

- `UnregisterShare` dereferenced the root a broken share does not have, so
  removing a share whose disk had gone answered 500. That is the exact repair
  that had to work: it is the only one nothing else will ever undo.
- The manual retry left the health degradation standing until the next probe
  pass, so an administrator who had just fixed a share read a status still
  calling it broken with no way to tell a stale answer from a repair that did
  not take.

### Item not done

SMB work item 3, verifying that a bind-address or interface change reaches
smbd without a container restart, is untouched. It is explicitly "testing and
repair, not new machinery", and it needs the two-container harness with a real
SMB client attached; this machine has neither. The response half of the SMB
section, which is the part that needed code, is done.

## Work items

### Missing share path

Today a share whose path fails registration at startup is left unregistered
and recorded as a health degradation (`RejectedShare`,
`ReasonShareRejected`): the health endpoint knows, but the share is absent
from `Core.Shares()`, so the browsing UI and the admin share list simply do
not show it. A path that disappears while the server runs is worse: nothing
re-probes, so it errors on access. Instead:

1. On engine start and on the watcher's invalidation pass, each share root is
   probed. A root that fails to open is marked broken, not dropped.
2. The share list still shows a broken share, marked with its error ("the
   folder /srv/photos no longer exists"), for every user who could see it.
   Entering it shows the same message instead of a generic failure.
3. An administrator gets, on the share's own page: retry (the path may have
   been remounted), edit the path (with the save-time probe), or remove the
   share. Retry and edit go through the engine-domain restart when the jail
   needs a new grant (phase 4 machinery).
4. A share that breaks while the server runs (unmounted underneath it) is
   caught by the watcher: the errno pattern (`ENOENT`/`ESTALE` on the root
   handle) flips it to broken instead of logging and hiding.

### Engine crash visibility

Phase 6 fronts a crash with `/emergency`. This phase adds the operator-facing
detail:

1. The degraded banner names the failing subsystem and the error, taken from
   the engine build's own refusal, not a generic "something went wrong".
2. Crash-loop detection: three engine failures inside a minute stops the
   retry loop and holds degraded mode, so the log is three attempts and a
   conclusion rather than an endless spin.

### SMB apply verification

The push channel exists and reports richly: the agent answers each apply
with a `Report` (what smbd did, missing share paths, missing credentials),
and the explicit apply endpoint (`POST /api/admin/smb/apply`) already shows
it. The gap is every other write that republishes SMB: `smbSink` runs on
share, grant and account changes, and on failure it only logs and degrades
the health endpoint. That stance (never fail the caller, because the
database write already committed) is right and stays; what is missing is the
response saying so:

1. A save whose SMB republish failed or applied with warnings carries the
   agent's report in the response beside the success of the write itself, so
   the administrator sees "saved here, not applied over there" at the moment
   it happens instead of on the health page later.
2. When the agent socket is configured but unreachable, the same response
   path names the socket, distinguishing "rendered but nothing applied it"
   from an agent that answered with a failure.
3. Verify the stop/start path applies bind-address and interface changes
   without a container restart; fix the gaps found. The existing
   `sc-smb-control` restart of smbd inside the container is the mechanism;
   this item is testing and repair, not new machinery.

## Acceptance criteria

- Unmounting a share's backing path while the server runs marks the share
  broken in the UI within the watcher's interval; remounting and pressing
  retry restores it without a container restart.
- Deleting a share's path and restarting the server still lists the share,
  broken, with edit and remove actions that work.
- An SMB save with the sidecar stopped reports the apply failure by name.
- An SMB workgroup change reaches a connected SMB client after the in-container
  smbd restart, with the container itself never restarting (covered by the
  existing smb e2e harness).
