Both are manifest lists covering amd64 and arm64, and every architecture was

**Read the two upgrade notes at the bottom before pulling.** One is a
forward-only database migration and the other may change what your existing
share links say about themselves.

## Four screens on the phone stop being dead ends

Search, the photo timeline, favourites and deleted files are all in the
navigation of both mobile apps, and none of them worked.

**Search never issued a request.** The Android client sends an `OPTIONS` to the
DAV mount first and gives up silently unless the `Allow` header names `SEARCH`.
It did not, so the search box returned nothing and reported no error. RFC 5323
`SEARCH` is now implemented, and `Allow` is composed at startup from the
methods that actually have a handler rather than being a constant. A build with
`--no-default-features` registers no search backend, advertises no `SEARCH`, and
still answers 405 for it.

**The photo timeline is a search.** Both apps build their media grid as a query
on the media type ordered by modification time, so it was blocked on the same
thing. It works now, including the date-window paging iOS uses.

**The star reverted.** `oc:favorite` was readable and nothing could write it: a
`PROPPATCH` landed in the dead-property store, answered 200, and the next
listing read the old value back out of the favourites table. It is a settable
live property now, and both the report iOS sends and the search Android sends
answer the favourites screen from the same code.

**Deleted files 404'd on every tap.** The capability document advertised a
trashbin and there was no route behind it. There is now, over the per-share
trash the core already had, with restore and purge and empty-all. Per-share
trash is still off by default, so on a default install that screen is correctly
empty rather than broken.

## Logging out from a phone actually logs out

Both apps call `DELETE /ocs/v2.php/core/apppassword` when the user removes the
account. There was no handler, so the app password issued during enrolment
stayed valid for the life of the server: the phone forgot the credential and
the server did not. It is revoked now.

Alongside it, an app password can be marked as belonging to a lost device from
the app-password list in Settings. That is deliberately not a revoke: a revoked
credential can no longer authenticate, so it can no longer ask whether it
should erase its local copies, and the files on the lost phone stay where they
are. The credential keeps working until the device reports it is done, and the
server retires it then.

Playing a video no longer downloads it whole first. The media endpoint hands
back a short-lived signed URL on the content origin that supports range
requests, so an external player can seek. It is `GET`-only, expires in ten
minutes, and is ACL-checked at issue time under the requesting account.

## Three path vocabularies had one name

This is the part with the visible bugs, and they all have the same cause. The
server addresses files three ways: the path a client sends, the path the web UI
sends, and the path the storage layer answers with, which carries the grant's
own subdirectory on the front. All three are a string. Every conversion at the
boundary got it wrong in the same direction.

**A share created from a phone could land on the wrong file.** The client's
path already names a grant, and the server prefixed the first grant's name onto
it a second time. Usually that resolved to nothing and the phone got a 404
about a share id it had never sent. When the first grant happened to contain a
same-named folder, the link was minted on that file instead, and the response
echoed back the path the client asked for, so it looked like it had worked.
Sharing a folder from Android could not succeed at all, because that client
appends a separator to a folder path and the extra empty component was
rejected.

**Every thumbnail in a grant rooted at a subdirectory was missing.** The same
doubled prefix, one layer down. With every grant sitting at its share's own
root the wrong answer and the right one coincide, which is why no test caught
it. The mobile photo grid is entirely thumbnails.

**Every top-level folder showed 0 B.** The first listing a client performs
after enrolment carried no size property at all. A grant root showed 4096
bytes, which is worse: it is the directory inode's own size, and it is
plausible enough that nobody reads it as an error. Both report their real
recursive size now, and a folder whose total genuinely cannot be computed omits
the property rather than substituting a number.

The two vocabularies are separate types now, with exactly one conversion
between them, so the next place that tries to do it by hand will not compile.

## Three writes that failed in silence

Two metadata renames and the cache invalidation on every write discarded their
error without logging it. The renames leave the database naming where a file
used to be, so a thumbnail for a renamed file resolves to a path that no longer
exists. The invalidation is worse: it leaves cached directory tags looking
fresh after a write that changed them, a sync client polls, sees the value it
already has, and never fetches the change. All three log now, and a failed
invalidation falls back to invalidating the whole share, which costs a
recompute and loses nothing.

## The capability document stops overstating

It claimed group sharing, which this server has never done and refuses at the
API. Neither client gates its people picker on that key, so the picker is still
drawn and still finds nobody; what changes is that the document no longer
describes a feature the server answers 400 for. The same correction covers user
and group share expiry.

## Upgrade notes

**The metadata database gains a column on first start.** It is a forward
migration with no downgrade path: an older binary started against the upgraded
database will not know about the column and will refuse the writes that name
it. Take the usual snapshot first if you keep one.

**Links minted through the compat share API before this release still point
where they always pointed.** Nothing moves them. What changes is that they now
report that path truthfully instead of echoing back the one the client asked
for, so a link sitting on a file nobody meant to publish becomes visible and
deletable rather than disguised. If you have ever shared from a phone, look
through your links once.
