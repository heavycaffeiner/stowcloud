# Release v0.10.0

Uploads from the Nextcloud and ownCloud clients work again, share links have a
screen of their own, and the recent list is the same list whichever client asks
for it.

## Fixes

- **Chunked upload**: A transfer's final chunk was refused, which ended every
  upload large enough to be chunked. The minimum chunk size applies to clients
  that choose their own offsets; a client that sends numbered chunks declares no
  total and its last chunk is whatever the file length leaves over, so the rule
  could never exempt it. Out-of-order chunks skipped the check entirely, so
  whether an upload failed depended on the order its pieces arrived in.
- **Truncated uploads were published as complete**: A transfer missing a chunk
  assembled without complaint and answered 201. The spool has nothing left to
  merge once the gap is past the write head, so assembly looked finished and the
  bytes received became the file's length. A sync client deletes its local copy
  on that answer. Assembly now checks the length declared when the transfer was
  opened and refuses a short one.
- **Resumed uploads**: Reopening a transfer failed, and the reference client
  resumes by re-running the whole operation. A resumed upload therefore died
  before its first chunk, and a client that lost the response to the first open
  could never proceed. Reopening now continues the existing transfer, or starts
  a fresh one when the previous session has expired or been abandoned.
- **Resumed uploads sent their opening bytes twice**: The chunk listing named
  the pieces already stored without saying how large they were. A client works
  out where to resume by adding those sizes up, so it restarted from the
  beginning while numbering past what it had already sent, and the assembled
  file repeated its opening bytes.
- **Upload failures reported as server faults**: An incomplete transfer, a
  chunk under the minimum, a checksum mismatch and an expired session all
  answered 500. A sync client retries a 500 forever and shows the reason phrase
  to whoever is holding the phone. They now answer as the client-side faults
  they are.
- **Created folders had no identity**: A folder created through the
  compatibility layer reported no file id, so the client held a folder it had
  just made with no id until something listed it again. The create now reports
  the same identity a listing does.

## Features

- **Share link overview**: A screen listing share links, at `/links`. An
  administrator sees every link published from the deployment together with who
  owns it, which is what an operator asked to take a leaked link down actually
  needs; an ordinary account sees only its own. The same administrative view is
  available to the Nextcloud app through the OCS shares endpoint with
  `all_links=true`. No listing carries a token: an overview crossing every
  account would otherwise hand its reader every visitor's access to every
  published file.

## Changes

- **One recent list**: The interface, the app's files screen and the app's
  recent screen each had their own idea of how far back "recent" reaches and how
  many rows it holds, so the same account saw a different list depending on
  which client it opened. All three now read one policy: a fourteen day window
  and a hundred rows unless the client asks otherwise, bounded at five hundred.
  A client's requested row count is honoured rather than dropped, and a window
  given as a plain timestamp is read rather than ignored.
