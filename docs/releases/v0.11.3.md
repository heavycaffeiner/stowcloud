# Release v0.11.3

The shared-files screen in the phone app listed nothing.

## The fix

- **One share id was too large for the client to read, and it cost the whole
  screen.** A share shared with an account, rather than by link, was numbered
  in a separate range starting above four billion. The client reads that
  number with a 32-bit parse, and a single number past the ceiling aborts the
  document it arrived in: not the one entry, the entire list. So one account
  share anywhere in the deployment emptied the screen, and left it reporting
  an error that named the sharee lookup. Both ranges now fit inside a signed
  32-bit integer.
- **An account share described itself as a public link.** It carried an empty
  link URL, and a client that finds a URL on a share files it under public
  links whatever the share type said. The row claimed a link the account
  never published, and offered it with no token behind it. An account or
  group share now carries no link URL at all.

The ids of account shares change with this release. A client holding an old
one gets "no such share" until it lists them again, which every screen does
before it shows anything.

## Verification

A link and an account share are listed together, and every id in both the
listing and the creation reply is read back through the same 32-bit parse the
client uses. The account share is then read the way the sharing panel reads
it, and checked for the share type it claims and the absence of a link URL.
Both fail against the previous release.
