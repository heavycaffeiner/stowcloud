# Release v0.12.6

`-addr` stays where it was told to listen.

## A settings save moved the socket

The flag says it overrides the stored address, and it did, until the next
save of any section. Saving a search setting, or a rate limit, or anything
else, re-read the stored network document, found no bind address there, took
the compiled default of every interface, and moved the listener to it.

A deployment started with `-addr 127.0.0.1:8080` behind a reverse proxy was
therefore published on `0.0.0.0:8443` by an administrator saving something
unrelated to the network. The log said "the listener moved" and nothing said
why it should not have.

An address given on the command line is now pinned for as long as the
process runs: no stored setting moves it. An address that was not given on
the command line still comes from the stored setting and still moves when
that setting is saved, which is what it is for: an operator who bound
somewhere unreachable changes it from the screen.

## Verification

Two tests over the real HTTP surface. With a pinned address, saving an
unrelated section leaves the listener where it is; without one, saving the
network section moves it to the address that was saved. Removing the pin puts
the first test back to "the save moved the listener to 0.0.0.0:8443", which
is the defect as it shipped.
