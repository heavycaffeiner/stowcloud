# Release v0.12.1

Search from the phone app answered the wrong question three ways, and the
web filters moved into a menu.

## Search from a Nextcloud client

Three defects, all in what the compatibility layer did with a search:

- **It stopped at a hundred rows.** The app's search screen sends no row
  count, and an absent count was read as "give me a page". A folder with 315
  matches answered with 100 and nothing said so. A stated count is now
  honoured exactly, and an absent one asks for every match: no ceiling, and
  no three-second walk deadline either, since a list cut short by a timer
  looks exactly like a list of everything there is.
- **The scope in the request was a suggestion.** A SEARCH body names the
  subtree to look in. It was passed to the ranking and nowhere else, so a
  search scoped to one folder answered with matches from its siblings: a
  destination picker offered folders from outside the tree it asked about.
  The scope now decides where the walk starts, and a scope naming nothing
  the caller can search answers empty rather than account-wide.
- **The unified search panel dropped every folder and mislabelled every
  path.** Folders were filtered out of the result list, so typing a folder's
  name found nothing, and each entry carried its share-relative path rather
  than the one the account navigates: tapping a result opened
  `/reports/file` when the file is at `/Files/reports/file`.

## The search filters moved into a menu

## What changed

Nine chips sat between the query box and the results: three for what to look
for, six for the file-type groups. They wrapped onto two rows on a narrow
sheet and pushed the results down the panel to say what was usually "no
filter at all".

They are one button now. It opens a menu holding the same choices, marked
with a check where they are on, and the button says how many are on. What is
active is spelled out beside it, so nothing is hidden behind a click. The
extension box stays where it was, since typing into a menu that closes on an
outside click is a trap.

Escape now belongs to the menu while the menu is open. It used to reach the
sheet underneath and close the whole search in one press.

## Fixed on the way

The sheet clipped and displaced the menu. A `translate` in its entry
animation made the sheet a containing block for anything fixed inside it, so
the menu was cut off at the sheet's edge and offset by the sheet's own
position. The sheet fades in now, and does not clip.

## Verification

Against a running engine holding 300 files and 15 folders whose names all
match, driven with the exact SEARCH body the Android client builds: an
unstated limit answers 315 rows including all 15 folders (it answered 100
before), a stated limit of 7 answers 7, and a search scoped to one folder
answers its 12 files and nothing outside it (it answered 100 rows from every
folder before). The unified search endpoint reports a matching folder with
the path `/Files/target-dir` rather than `/target-dir`. Recent and gallery
searches, which share the row-count rule, still answer. Each fix is pinned
by a test that fails when the fix is removed.

Driven in a browser: the menu opens anchored under its button (button left
256, menu left 256, top 4px below), holds all nine rows without clipping,
keeps its place while several are toggled, and each toggle re-runs the search
(files 800, files plus documents 800, folders 20). Choosing folders drops the
type rows and says why. Escape closes the menu and leaves the sheet open;
the next Escape closes the sheet and returns focus to the toolbar button. On
a 412px viewport the same menu arrives as a bottom sheet.
