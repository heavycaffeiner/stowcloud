# Release v0.12.12

Paths are picked rather than typed from memory, shares list in the order each
account wants, and the search index says what it is doing.

## A path field has a browse button beside it

Every place the interface asks for a path on the server, the first-run
wizard's first share, the folder-share dialog's server path and VeraCrypt
container, and the homes root, thumbnail directory and single-sign-on CA file
in server settings, now carries a button that opens a picker. Typing is still
the default and nothing about it changed.

The picker lists what this server can actually open. Under the sandbox that is
the mount points it was granted at boot plus the folders already registered as
shares, discovered by trying to open each one rather than by reading
permissions, which Landlock does not appear in. A path the server would refuse
is therefore one that never appears. During setup the same listing is served
against the setup token, which is checked without being spent.

## The shares list in the order the account chose

The sidebar's root list has a reorder control. Moving a root saves the order
against the account, so it is the same order after a sign-in somewhere else.
A root the order has never heard of keeps its place at the end rather than
disappearing.

## The index build reports what it is doing

Progress reached the database only every ten thousand names, so a corpus
smaller than that reported nothing at all until it was already finished: a
spinner, then "done". It now reports every five hundred.

The admin screen shows the index's own state rather than only the build
button: off, on and empty, holding a count of names, or covering less than the
corpus and therefore being skipped by every search. While a build runs, that
screen shows its live count and then how it ended, and the button stays
disabled until then rather than for the second the request took.

A rebuild used to stack a second copy of every name on top of the first: the
merge that folds them ran only past a ratio. It now runs after every build, so
the count an operator reads is the corpus rather than a multiple of it.

A finished job with no item total announced "0 items processed", which is what
an index build always is. It announces the count it reached.

## A running search says what it is looking through

A search of a large tree can go a long time before its first match, and
silence for that long reads as a search that has stopped. The stream now
carries the walk's counters, and the panel shows how many folders have been
looked in beside the number found.

## Verification

Driven in a browser against running engines: the picker opens over the share
dialog, browses, and writes the absolute path into the field, on the setup
wizard with a token and on both admin screens, in folder mode and file mode;
reordering two shares survives a reload; a build of a 12,302-name corpus shows
9,500 mid-run and 12,302 at the end, with the index then holding 12,391 names
rather than twice that; and the search stream carries a progress frame before
its done frame.
