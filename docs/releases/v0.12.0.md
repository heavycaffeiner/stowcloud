# Release v0.12.0

Search is a surface of its own, it filters, and it runs to the end.

## Search runs to completion

The old search stopped twice over: at a thousand results, and after three
seconds of walking. Both cuts were invisible in the answer, so a query with
1,200 matches looked like a query with 1,000, and a share too slow to finish
contributed nothing while the list read as complete.

The streaming route now sets no result ceiling and takes no deadline. Matches
are written the moment the walk finds them, one directory at a time, so the
first names are on screen while the rest of the tree is still being read. The
terminal event carries the count and the elapsed time instead of two flags
about being cut short. What stops a search early is the reader leaving: a
failed write cancels the walk, so a closed tab releases the worker slot
instead of paying for a screen nobody is watching.

The three-second deadline and the thousand-result cap still apply to every
other caller, including the Nextcloud compat surface, which asks for a bounded
answer and gets one.

## Filters

A query may narrow itself two ways, and both are answered rather than
approximated:

- **Kind.** Files only, folders only, or everything. A filter never prunes the
  traversal: a folders-only query still descends into folders to find the ones
  underneath.
- **Extension.** A list of up to 128 extensions, folded for case. A folder is
  never admitted by an extension filter, because a directory named
  `photos.jpg` is not a picture. Presets (Images, Documents, Video, Audio,
  Archives, Code) are shortcuts for typing the list; what travels is always
  the extensions themselves, so a format the presets forgot is one keystroke
  away. The ceiling is high enough that selecting every group at once still
  sends every extension: a filter quietly cut down to fit would answer a
  narrow question with a short list.

An unreadable `kind` or `ext` is refused with 422 rather than dropped: a
client that asked for folders and was handed the whole tree has no way to
tell its filter went missing. So is asking for folders with an extension,
which can match nothing anywhere and would otherwise walk every share to say
so.

A streamed search always walks. The name index holds no folders at all and
trails the filesystem by however far behind the updater is, which a bounded
query can live with and a search promising every match cannot. Bounded
callers, the Nextcloud compat surface among them, still take the index.

## The search surface

Search used to be a text field in the browse toolbar that dropped a hundred
paths over the file list. It is now one panel with two shapes:

- **Desktop:** a top sheet over the page you were on, so closing it returns
  you to the folder you started from. Ctrl+K, or Cmd+K, opens it from any
  screen in the shell.
- **Phone:** a screen of its own at `/search`. Deliberately absent from the
  navigation bar and the drawer: search starts from where you are.

The result list carries each match's name, its folder, its size and its
modification time, and it is virtualised, so 2,500 hits render 18 rows. A
live count runs while the walk does, ordering settles once the stream ends,
and the sort can then be changed to name, size or modification time. The
folder the search started from is sent as the ranking scope, which lifts that
subtree without confining the search to it.

Two details that a whole-tree search makes matter. The typed extension box
commits on Enter or on leaving it, never per keystroke, because each commit
starts a walk of every share. And a search that finds nothing while a filter
is on says which filter, since the usual reason is an extension left over
from the query before it.

## Verification

The engine tests pin the parts that were silently short before: a query
matching 2,400 files reports 2,400 over the wire and counts them in its
terminal event; a streamed walk's set of paths is compared against the
collecting walk's, so a lost directory or a duplicated hit fails where a
count would not; a streamed query with an index attached is checked to walk
and to find both the folder and the file the index never received; each
filter is checked against a corpus holding a folder and a file with the same
name and extension. The truncation defects were reproduced first by breaking
the fix and watching the tests fail.

The interface was driven in a browser against a live engine: 2,480 matches
across 2,520 entries streamed in 11 ms and rendered 26 rows, the kind and
extension filters re-ran the query and returned 80, 2,400 and 1,200, a result
opened its folder and closed the sheet, Ctrl+K opened it from `/recent` with
the field focused, Escape closed it without navigating, and the phone
viewport landed on `/search` with no search entry anywhere in the navigation.
Typing an extension letter by letter started no search until Enter, the
Documents and Code groups together sent all 40 of their extensions, and
switching to folders cleared the type filters and said why.
