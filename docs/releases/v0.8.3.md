# Release v0.8.3

This release enforces subpath boundaries across trash operations, cleans home directories when accounts are removed, bounds public drop uploads and audit log growth, records the real visitor address behind a tunnel or sidecar proxy, corrects permission error reporting so a refused upload or delete says it was refused rather than reporting the item as missing, and stops the interface offering actions the account's grant forbids.

## Fixes

- **Trash isolation**: Trash listing, restore, and purge now evaluate permissions on the entry's original path instead of the caller's root, so a subfolder-scoped grant can no longer read or delete another subfolder's trashed entries.
- **Home directory cleanup**: Deleting an account removes its home directory, so a newly created account reusing the same name no longer inherits the previous account's files.
- **Drop link limits**: Public drop links enforce the request body limit and charge storage quota, instead of accepting unbounded payloads in memory.
- **Audit retention**: Audit entries are pruned against a retention policy, and cursor pagination stays correct on sparse queries.
- **Listing performance**: Directory listings and walks drop redundant stat calls and repeated permission evaluations, and upload chunk handlers stream request bodies instead of buffering them on the heap.
- **Permission errors**: An action refused by an access rule on a folder the account can already see answers 403 with `fs.denied` rather than 404. The interface renders it as "No permission" for uploads, deletes, moves, copies, folder creation, renames, trash operations, and folder size measurement, where it previously showed a generic failure or nothing at all.
- **Upload refusals**: A 403 during upload session creation or chunk transfer stops the transfer immediately and names the permission refusal, instead of consuming the retry budget and reporting "out of retries".
- **SMB password after disabling two-factor**: Turning two-factor authentication off now restores the account password as the SMB credential, using the password the dialog already re-confirmed. Previously the credential row deleted at enrollment was never recreated, so SMB stayed unusable and the settings screen kept reporting no credential.
- **Administrator tabs**: The tab bar on the administrator screen spans the full content width like the settings screen, instead of collapsing to its labels and leaving the underline short.
- **Client address behind a proxy**: A peer that is not itself on the internet, which is what a tunnel daemon or a sidecar proxy is, is trusted with no configuration, so the audit log and the login rate limit record the address it forwards instead of one container address for every visitor. A configured trusted-proxy list still decides on its own, and a caller arriving straight off the internet is never believed. This also closes the repair door to internet visitors on such a deployment, which previously read the proxy's private address as the client's.
- **SMB credential restored on sign-in**: An account that is eligible for SMB and holds no credential gets one sealed from the password it just signed in with. The settings screen said signing in again would start SMB working and nothing did that, so the screen kept reporting no credential however often the account signed in. An account with a second factor enrolled is left alone, which is what keeps the account password from bypassing that factor.
- **Settings field notes**: The notes explaining what an empty app-host or trusted-proxy field means render as sentences. The server sent keys the interface had no text for, so the raw key was shown, and the note explaining an empty SMB server name was never requested at all.
- **Text editor saves**: Saving in the editor works. Every save sent an `If-Match` condition against a metadata-derived change token, which the server refuses by design, so every save failed with "could not save". The editor now compares the token it loaded against a fresh one taken at save time and offers the conflict choice only when the file really moved.
- **Actions the grant forbids**: The listing reports what the account may do to the folder itself, and the interface reads it. Upload, folder upload, "new folder", and the drop target appear only where files may be created; rename, delete, download, duplicate, and share appear only on rows that allow them. The destination picker names a folder the account cannot write to and keeps both transfer buttons disabled, instead of accepting the choice and failing afterwards.
- **Refusal messages**: The wire codes the interface translated had drifted from the ones the server sends, so a refused save, a full disk, an unusable name, and a locked item all rendered as a generic fallback. Locked items now have their own message.
- **Upload tray**: A tray with nothing in flight reported "Upload done" whatever its rows said, so a batch refused outright announced itself as finished. It now reports how many failed, and a failed row can be cleared.
- **Search index build**: Starting a build reported that it could not start, while the build was in fact running: the response was read for a field no route sends, so the progress tray polled a job id of `undefined`. The build now appears in the tray and runs to completion.
- **App passwords**: A credential revoked by a wipe request reads as expired instead of live, and no longer offers to ask the device again.
