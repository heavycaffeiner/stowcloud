# Release v0.10.2

Eight fixes to the Nextcloud compatibility layer, found by auditing it against
the Android, iOS and desktop clients at their current releases. Every one of
them is something a real client does that this server answered wrongly.

## Fixes

- **Large uploads were reported as failures**: The desktop client reads the
  file's identity from the reply that publishes a chunked transfer and treats
  its absence as a failed upload. That header was never sent, so every file
  above the chunking threshold landed on the server intact and was still shown
  as failed, and the client retried it on the next sync.
- **The account always looked full**: Free space was reported as zero on every
  deployment. The path being measured was built with a trailing separator,
  which cannot be parsed, so the measurement never ran. A client compares the
  file it is about to send against that figure and holds the upload while it is
  smaller, so uploads were refused on storage with room to spare.
- **The iOS app reset its stored quota**: Looking an account up by its own
  login name answered without the quota block. The app refreshes its profile
  from that route on every server check and writes what it parsed over the
  record it holds, so the account read as full there too.
- **Opening a file by id opened a different file**: A search by file id was not
  recognised and fell through to the recent-files listing. The client takes the
  first row without checking which file it names, so a notification or a link
  opened whichever file had been touched most recently.
- **The recent screen was empty**: A search for a date range sends its bounds
  as separate terms under one property. The upper bound was taken as the start
  of the window, so the listing asked for files modified after the range had
  already ended.
- **Photos were dated when they synced**: Both phone clients declare a file's
  own modification time on an ordinary upload, and only the chunked path read
  it. A picture therefore carried the moment it reached the server, and since
  the gallery orders on that date, a camera roll sorted by sync order rather
  than by when the pictures were taken. Uploads also no longer come back down:
  the desktop client compares the server's timestamp against its own record and
  was re-downloading files it had just sent.
- **The photo tab never reached the end**: The gallery pages by narrowing a
  time window and asking for a fixed number of rows. Neither the window nor the
  count was applied, and the rows that were returned were not ordered, so each
  scroll re-sent the whole library and files could be skipped for good.

## Changes

- **The release gate rejects reference source in the tree**: The Nextcloud
  clients are kept alongside this repository so their behaviour can be read.
  They are licensed differently, and nothing prevented a line of theirs from
  being pasted into this codebase. The gate now refuses one, and is verified in
  both directions: against a planted copy and against the tree as it stands.

## Known limits

- **Sync clients upload into a share, not the account root**: This server's
  root is the list of shares an account was granted rather than a folder, so an
  upload aimed at it answers 404. In the mobile app, set the auto-upload folder
  to a path inside a share, such as `/Photos/Camera`, and pick a folder inside
  a share when uploading by hand. Uploads into a share work throughout,
  including resumable transfers of any size.
- **Sign-in by QR code or managed configuration is not served**: Those two
  paths exchange an account password for a device credential over an endpoint
  this server does not implement, because it accepts no account password on an
  HTTP header. Sign in with the login flow, which every client offers and which
  is unaffected.
