# Release v0.12.5

The WebDAV surfaces stop handing the server's request object to the database.

## A request context that outlived its request

Both WebDAV mounts, this server's own and the compatibility one, are net/http
handlers bridged onto fasthttp. The bridge hands over fasthttp's request
object as the request's context, and that object is rewritten when the server
shuts down and again when it is reused for the next request. fasthttp
documents retaining it past the handler as forbidden.

Every `database/sql` query installs a cancellation watcher on the context it
is given, which is exactly such a retention: a listing that reads an owner's
group names left a watcher holding the request object behind. The race
detector reports it as a write from shutdown against a read from the listing.

Both bridges now run on a context of their own: the values the chain resolved
survive, no watcher is installed on the request object, and it is cancelled
when the handler returns, so work is bounded to the request exactly as
before.

Nothing observable changes. fasthttp's request context is cancelled at
shutdown and at its own timeout, neither of which a handler was reacting to,
and a client that disconnects is still noticed by the write that fails.

## The detector had nothing to say about the compatibility layer

The verification gate's race step ran `go test -race ./...` with no build
tag, so the entire Nextcloud compatibility surface, every WebDAV and OCS test
it has, had never been under the race detector. That is why this survived.
The gate now runs the detector over both tag sets.

## Verification

The failing invocation is clean: the compatibility layer's whole test package
under `-race`, including two runs of the same test in one process, which is
what surfaced the shutdown write in the first place. The defect reproduces on
v0.12.0 with a test this round never touched, so it predates the search work.
The gate ran green with the second race step in place.
