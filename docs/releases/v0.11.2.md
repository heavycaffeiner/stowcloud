# Release v0.11.2

Sharing from the phone app did not work: the sharing panel of every folder
closed with "unable to fetch sharees", no folder could be shared, and the
shared-files screen stayed empty.

## The fix

- **A path spelled the way a client spells it was read as absent.** A client
  writes a folder with a trailing separator, and the path it asks about is the
  path it shows, so `/documents/` arrived where `/documents` was expected.
  Resolution splits a path on that separator, so the request named a path with
  an empty last component and answered as not found. Two screens are built on
  that one request: the sharing panel lists the shares of a path before it
  opens, and the share it creates posts the same path back. Both now accept
  either spelling, and the account root, addressed as the separator alone or
  as nothing at all, answers the shares it holds rather than a refusal.
- **A deployment with no upload engine blamed the verb.** The chunked upload
  collection answered every method as one it does not allow, when what is
  true is that the collection is absent. It answers 501 now, and the message
  says so. The capabilities document already reported chunking as
  unavailable, and one client ignores that and tries anyway, so the refusal
  is the only thing that tells whoever is holding it what happened.

The sharee search itself was never at fault. The app's own message names it,
but the request behind that message is the share list for the file being
shared, which is what was failing.

## Verification

The three screens are now driven end to end in the test suite, in the order
the client runs them: list the shares of a path in every spelling a client
sends, create a share on a folder and find it in that folder's own panel, then
list what the account shared and read each path back. Each one fails against
the previous release.
