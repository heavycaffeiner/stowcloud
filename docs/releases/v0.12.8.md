# Release v0.12.8

A shutdown waits for a copy to finish recording what it did.

## A copy outlived the request, then outlived the databases

A recursive copy is answered 202 and runs on after the request that started
it. It was untracked: nothing counted it, so a shutdown closed the databases
underneath it. The copy then wrote its outcome into a closed database, logged
that as a failure, and left the row a client polls reading as one the runner
never finished.

The engine now closes the sockets and the watcher, stops the size guard,
drains the work a request started, and only then closes the databases. The
drain is bounded at ten seconds; past that the close reports what is still
running rather than holding a restart open.

## Verification

A copy of sixty files started through the HTTP surface, the engine closed
while it runs, then reopened on the same data directory: the operation row
reads done. With the drain removed it reads running. The same copy through
the WebDAV mount now drains instead of polling the destination for five
seconds, which is what made that test flake once in CI.
