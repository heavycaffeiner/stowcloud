# Release v0.12.9

A shutdown asks the detached work to stop, then waits one item for it.

## The wait was bounded by a clock

The previous release made a close wait ten seconds for a running copy. That
left the case it was written for untouched: a copy of a large tree outlives
ten seconds, and then writes its outcome into a closed database exactly as
before.

The close now tells the work to stop before it waits. A copy reads that at
the same item boundary where it already reads a cancellation, so the wait is
one more item rather than a whole tree, and the timeout is only a backstop
for an item that is itself long. A copy stopped that way is recorded
interrupted: the state a client reads as work still theirs and not resumed,
rather than one the runner never reached.

## The index build was the other one

An index build is detached the same way and takes minutes on a real corpus,
so a close during one was the same defect with a wider window. It is now
counted and stopped alongside the copies. The long-lived loops are not:
they end on their own cancellation, and joining them in a close would hang
it rather than drain it.

## Verification

A copy of sixty files started through the HTTP surface, the engine closed
while it runs, then reopened on the same data directory: the operation row
is terminal. With the stop-and-wait removed it reads running, five runs out
of five. A copy started against an engine already stopping records
interrupted. The WebDAV fixture drains its own jobs before its databases
close, which retired the counted wait in the recursive-copy test.
