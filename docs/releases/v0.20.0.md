# Release v0.20.0

This release adds automatic private Home folders, owner-only SMB access, and parent-folder navigation. It also includes the server runtime and web interface updates made since v0.19.1.

## Home folders and SMB

Enabling Home folders prepares private storage for existing accounts and new accounts before their first web sign-in or SMB connection. Creating an account no longer requires opening a shared-folder permissions dialog when Home is enabled. Administrators can add shared-folder permissions separately, inspect Home preparation status, and retry preparation failures.

Home is a managed personal folder rather than an editable shared folder. Manual changes to its share and permissions are blocked. Existing numeric Home paths are preserved, and legacy Home permissions that exposed the common tree or another account's directory are removed when Home is enabled.

SMB publishes each ready Home as a hidden, owner-only share such as `\\nas\Home-alice`. Settings → Connections shows the current account's Windows and macOS/Linux addresses, copy buttons, authentication state, and folder availability. Missing container mounts, unapplied credentials, unavailable storage, and unsupported permissions are reported separately. Personal SMB shares do not follow symbolic links.

Account, credential, grant, group membership, Home, and share changes update SMB publication immediately. Credential and share changes terminate established SMB connections so the new rules apply; unchanged publication keeps connections open. Credential synchronization failures stop SMB until synchronization succeeds. A denial anywhere inside an ordinary share excludes that account from the SMB share instead of granting access beyond its web permissions.

Deleting accounts and groups now refreshes cached permissions immediately. A recreated account cannot inherit the previous account's cached Home or shared-folder access. A nonempty Home directory without an ownership grant is refused, preserving old files without handing them to a new account; move that directory aside before retrying preparation.

## Parent-folder navigation

File lists and grids show a clickable `..` item in every subfolder, including empty and filtered folders. It uses the same row or card layout as ordinary folders, with no checkbox and reserved control spacing to keep icons and names aligned across densities and phone layouts. It is hidden at the top level of each shared folder, including Home. Public links stop at the linked folder, and server path selection stops at the root reported by the server. The navigation item is excluded from file selection and file operations.

Oversized public-link uploads now drain a bounded remainder before answering `413`, so declared and chunked uploads receive a readable refusal instead of a connection reset. The upload limit is unchanged, and rejected uploads do not create files.

## Web interface

The interface now uses shared Stowcloud components built on Mantine, common design tokens, TanStack Router and Query, and virtualized file and administration lists. Desktop and phone layouts have updated dialogs, menus, search filters, and selection actions. Phone selection actions fold into an overflow menu instead of growing beyond the available width.

## Runtime and package architecture

The server now starts through Hanami application bootstrap and Fx composition. Hanami owns process lifecycle, readiness, shutdown, managed listener generations, and Linux security handoff. Gin remains at the HTTP transport edge. Feature, storage, transfer, search, and worker services do not depend on HTTP framework request types.

The previous server tree is removed. Product implementation now lives under `backend/internal`, split into application composition, feature services, platform services, runtime ownership, HTTP transport, and bootstrap packages. Browser implementation lives under `frontend/src/features` with shared UI and library code.

The native JSON API is split by transport needs. Conventional request-response routes use Huma through the Gin adapter, which provides typed inputs, generated OpenAPI, and startup verification against the route table. Streaming, resumable upload, WebDAV, compatibility, and browser shell routes stay on their protocol-specific Gin or `net/http` adapters. The authenticated administrator specification is available at `/api/v1/admin/openapi`; Huma's public documentation and schema routes are disabled.

Fiber and fasthttp dependencies, adapters, compatibility helpers, and derived transport code are removed.

## Reusable modules

Builds and CI use Go 1.27.2, including the security fixes published on October 8, 2026. The HTTP/2 dependency is updated to `golang.org/x/net v0.60.0` to clear the corresponding release-time vulnerability findings.

Stowcloud now consumes released modules without local replacements:

- `github.com/heavycaffeiner/hanami v0.2.0`
- `github.com/stowcloud/durablefs v0.1.0`
- `github.com/stowcloud/namesearch v0.1.0`
- `github.com/stowcloud/storage v0.3.0`
- `github.com/stowcloud/transfer v0.2.0`
- `github.com/stowcloud/sandbox-worker v0.1.0`

Browser content encryption now imports `@stowcloud/rclone-crypt` from the public GitHub `v0.1.0` tag pinned to commit `eb48c44602f568a783b5b7aa34c02ee7ea55b09d`. The package is not yet available through npm; the Git tag is the distribution source until registry publication is possible.

Search keeps Stowcloud-specific VFS, authorization, live-stat filtering, product limits, HTTP, SSE, and Nextcloud behavior in this repository. The published namesearch module owns the storage-neutral query and index contracts.

## Upgrade and rollback

The included Compose file now requires Docker Engine 26.0 or newer and a current Docker Compose release for volume subpath mounts. Update the Compose file when upgrading. It mounts only the existing data volume's `homes` subtree into the SMB container at `/var/lib/stowcloud/homes`, preserving existing Home files while keeping the server database and master key outside that container. A custom Home root must be mounted at the same path in both containers and must not overlap an ordinary shared folder.

Turning Home off preserves its files and removes access. Changing its root does not move existing files. SMB clients may need to reconnect when credentials or share settings change.

The state database gains schema version 20 for direct-transfer publication receipts. The migration preserves existing account, share, upload-session, and file records, but a v0.19.1 binary refuses to open a version-20 state database. Other persistent formats remain unchanged.

For rollback, stop the new server and restore a complete pre-upgrade snapshot before starting v0.19.1. A binary swap without restoring the schema-19 snapshot does not work. Preserve the data directory, share data, and SMB rendered configuration. Do not copy the runtime SMB control socket. Confirm that uploads or other writes accepted after the snapshot are reconciled before restoring it, or they will be lost.

Security policy changes still require an external process replacement because an installed Landlock domain cannot be widened in place.

## Verification

The repository gate covers Linux AMD64 and ARM64 builds, non-Linux build tags, vet, lint, regular and compatibility tests, the race detector, vulnerability scanning, the frontend build, embedded UI checks, and browser interaction. Container CI builds and smokes the core and SMB images for AMD64 and ARM64.

The Home and navigation changes passed the backend and compatibility tests, lifecycle race checks, all 456 frontend unit tests, and 24 desktop and phone browser regressions. Real Samba checks covered reads and writes, owner isolation, hidden personal shares, symlink refusal, active-session revocation, password changes, and Home disable/re-enable without losing files. A Docker volume subpath check verified that existing Home files remain accessible while the database and master key remain outside the SMB mount.

The complete desktop browser suite also passed all 59 active tests. The optional README screenshot regeneration test is excluded from regular runs.

## Container images

The release workflow builds and smokes the core and SMB images on Linux AMD64 and ARM64. Once the release tag passes, it publishes `ghcr.io/heavycaffeiner/stowcloud:0.20.0` and `ghcr.io/heavycaffeiner/stowcloud-smb-daemon:0.20.0`.

Existing Compose deployments can update with `docker compose pull` followed by `docker compose up -d` after taking a stopped durable-state backup.
