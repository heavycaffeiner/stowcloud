# Release v0.12.2

The search index holds folders, and the folder picker gets folders.

## Folders are indexed

The name index held file names and nothing else. Every search that ran
through it therefore answered a shorter list than the same search answered
without it: the folder someone typed the name of was missing, and which
answer a client got depended on whether an administrator had turned the
index on.

A build now indexes a folder as it descends through it, and the incremental
updater keeps folder names current the same way it keeps file names current.
Nothing else about the index changes: a hit is still revalidated by a stat
before it reaches anyone, so what a folder is today decides how it is
reported.

## The folder picker asks for folders

A client choosing a destination sends `d:is-collection` beside the name
comparison. The compatibility layer parsed the element and then ignored it,
so the picker was answered with files: a list of destinations that cannot
hold anything. It is now read as the folders-only filter it is, and the
walk that answers it offers folders to the predicate rather than skipping
them outright.

## Verification

Against a running engine with the index built, holding 120 files in 8
folders: an unlimited search answers 128 rows including all 8 folders, the
same search with a stated limit of 200 goes through the index and answers
the same 128 including the folders (it answered 120 before), and a
`d:is-collection` search answers exactly the 8 folders. The unified search
panel reports the folder `reports-03` beside the files inside it. Both fixes
are pinned by tests that fail when the fix is removed, and the tier
equivalence tests now assert that the walk and the index agree about
folders rather than that they disagree.
